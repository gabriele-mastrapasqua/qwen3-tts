# The small model couldn't do emotion. So we stopped trying to give it one.

*For months, `--emotion` did nothing on the 0.6B. Steering failed. Fine-tuning failed. Then a
question from the right angle — "if cloning works on the small model, doesn't that mean you can
change the timbre?" — turned the problem inside out. Emotion, paralinguistics and voice cloning
now all run on the small model together, at **RTF 0.78**.*

---

## The wall

[qwen-tts](https://github.com/gabriele-mastrapasqua/qwen3-tts) is a pure-C inference engine for
Qwen3-TTS. It ships two model sizes: a 1.7B and a 0.6B that differ **only in width** — same 28
layers, same heads, same code predictor, hidden size 2048 vs 1024.

On the 1.7B, emotion is solved. You pass `--emotion anger` and the engine applies a steering vector
to the residual stream at layers 21-25. It works on presets, on cloned voices, in ten languages.

On the 0.6B, the same flag did **nothing**. Not "worked badly" — the engine gates it on
`hidden_size >= 2048` and it silently does nothing at all.

That gate was earned. We measured why:

- The 0.6B **does** have emotion: identical sentences produce a 17-22% activation shift for
  emotional content, comparable to the 1.7B's 20-30%.
- But it is **entangled**. Cross-emotion separability is worse at every layer: best-layer mean
  cosine **0.49** vs the 1.7B's 0.33; at layers 21-25, **0.59** vs **0.24**.
- Worse, the 0.6B's emotion identity is strongest **early** (L0-6) — exactly where language lives.
  Steer there and the pronunciation collapses. Steer late, where it's safe, and the emotions are
  0.59-collinear: you move timbre, not feeling.

We tried everything the big model taught us. Native 1024-dim steering vectors at every band and
weight. A multi-emotion CSP fine-tune. Per-emotion fine-tunes, one file each. Fine-tune plus
steering combined. Every single one failed by ear. The verdict was written down and the epic
parked: *emotion is a 1.7B feature; the 0.6B is the fast neutral TTS.*

## Killing the obvious idea, properly

When we came back to it, the first instinct was the obvious one: the big model has good emotion
directions, so **import them**.

Two facts made that worth checking rather than assuming. The models share an architecture. And the
Code Predictor — the 5-layer network that expands each frame into 16 codebook tokens — has
**identical shapes in both models**: hidden 1024, intermediate 3072, the same `lm_head` dimensions.
A perfect bridge, apparently.

So we measured the cosine similarity between the two models' Code Predictor weights:

| tensor | cos(0.6B, 1.7B) |
|---|---|
| `layers.0.mlp.gate_proj` | **-0.0007** |
| `layers.2.self_attn.q_proj` | **-0.0003** |
| `layers.4.mlp.down_proj` | **-0.0005** |
| `lm_head.0` / `lm_head.14` | -0.0025 / -0.0036 |

Cosine ≈ 0. **Orthogonal learned bases.** For scale: the Base and CustomVoice variants *of the same
size* sit at 0.9999. Same architecture, two independent trainings, no shared coordinate system.

This is a five-minute measurement that kills an entire family of ideas — steering-vector transfer,
learned linear maps, τ-vectors, anything that assumes a direction in one model means something in
the other. It also explains, retroactively, why an earlier ridge-regression map from 1.7B to 0.6B
activations had *negative* R² at every layer. That was never a data-starvation problem.

## One thing genuinely is shared

While measuring, we checked the speech tokenizer — the codec that turns discrete tokens into audio:

```
md5 qwen3-tts-{0.6b,1.7b}/speech_tokenizer/model.safetensors
  ccf5bd95ff388925556b42371ff72502   (682 MB — IDENTICAL)
```

Bit-identical. Same encoder, same decoder, same vocabulary. **Codec token N is the exact same
acoustic event in both models.** Not the hidden states, not the weights — the *codes*.

That suggested feeding the 0.6B an emotional codec prefix generated by the 1.7B: in-context
learning, emotion by example. It worked — the small model continued an angry reference's style onto
new text. But it had two problems. It cost RTF 15.7, because the ICL prefix is 234 extra positions.
And a comment in our own code, which we had quoted while ignoring half of it, explained the second:

> `ref_codes are BOTH the identity carrier AND the prosody template`

The reference's codec frames carry the donor's **timbre** too, and they overpower the loaded
speaker embedding. Feed an angry *Ryan* reference to a cloned *Galatea* voice and you get Ryan. Our
log line cheerfully said "identity unchanged". It was wrong, and a listener caught it before the
measurement did — x-vector cosine 0.9882 toward Ryan, 0.9486 toward Galatea.

## The question that flipped it

Then came the observation that solved the whole thing, from the project owner:

> *If cloning works on the small model, that means you can change the timbre — so the emotion
> should come in through cloning too.*

Every failed attempt had been trying to **inject** emotion into the residual stream at inference
time. But the 0.6B clones voices beautifully. That's a working, high-bandwidth channel into the
model's identity conditioning that we had been walking past.

So: don't inject emotion. **Clone from emotional audio.**

> On the small model, emotion is not an inference-time lever. It is a **property of the voice**.

```bash
# 1. donor: ~25 s of the target voice, emotional (the 1.7B, where emotion works —
#    or any emotional recording of that voice, including a real one)
./qwen_tts -d qwen3-tts-1.7b -s ryan -l Italian --emotion anger --text "<~25 s>" -o donor.wav

# 2. extract the voice from that emotional audio (ECAPA encoder, 0.6B Base model)
./qwen_tts -d qwen3-tts-0.6b-base --ref-audio donor.wav --save-voice ryan_ang.bin

# 3. use it on the SMALL model — the 1.7B is no longer in the path
./qwen_tts -d qwen3-tts-0.6b -s ryan -l Italian --int8 --emotion anger --text "..."
```

The asset is **4096 bytes**. The verdict on the first listen was, verbatim: *"anger super
arrabbiato — this is a huge win."*

It works on cloned voices **and on presets** — a preset simply becomes a voice asset too. It
composes with inline `[laugh]`/`[sigh]` paralinguistic tags in a single generation. And because
there is no ICL prefix, it costs nothing:

| on the 0.6B | bf16 | **int8** | int4 |
|---|---|---|---|
| emotional voice (4 KB) | 1.16 | **0.73** | **0.56** |
| emotional voice (16.8 MB graft) | 1.14 | **0.72** | — |
| **emotional voice + `[tag]`** | 1.18 | **0.78** | — |
| bare 0.6B (reference) | 1.17 | 0.69 | — |

The entire expressive stack — cloning, emotion, paralinguistics — costs **0.09 RTF** over the bare
model. And int8 doesn't damp the emotion, which was the obvious risk: the emotion lives in the
conditioning, exactly the kind of subtle signal quantization tends to flatten. It survived.

## Three things we found on the way

**A voice is 4 KB, and the other 16.8 MB belongs to the model.** Our "graft" voice format is a
16.8 MB file. We diffed two of them, for *different voices* of the same model:

> They differ only in bytes 12..4158 of 16,806,036. Everything after is identical.

The speaker embedding, and nothing else. The remaining 16 MB — the pad/bos/eos embeddings and the
projection overrides — are properties of the *model*. So an emotional graft isn't an export, it's a
4 KB swap inside an existing file. And shipping N voices × M emotions costs one shared graft plus
**4 KB per cell**.

**Constants don't transfer between model sizes, even when methods do.** Our paralinguistic `[tag]`
system replaces a tag with an onomatopoeia inline, at a pinned per-tag seed. The method works
identically on the 0.6B. The seeds do not. `[laugh]` wants seed 2024 there, not the 1.7B's seed 7.

More interestingly, seeds **collide across tags**. On the 0.6B, seed 42 is a *yawn attractor*: the
laugh, wow and yawn onomatopoeia all land on a yawn there. Measured, then confirmed by ear —
`laugh_s42` and `yawn_s42` are the closest same-seed pair in the whole sweep. The vocal family
appears to be a small set of attractors, and the (onomatopoeia, seed) pair selects which one you
land in — not necessarily the one you asked for. That's actionable: `[yawn]` now *uses* s42, and
`[laugh]` avoids it.

**Off-the-shelf audio taggers can't hear these events.** Mapping tags by ear is the bottleneck, so
we pointed our CNN14 + CLAP screener at the sweep. It returned **zero** wins — every clip a human
calls a clean sigh comes back `MISS` with P < 0.05, on both backends. Cropping to the event region
didn't help. These taggers are trained on isolated, salient AudioSet events; a 0.4-second sigh
inside an Italian sentence is drowned by the speech.

We also found a beautiful-looking heuristic — falling F0 predicts a performed event, 3 tags out of
3 — and then killed it on a held-out set, where it ranked the known winner *last*. It had been
fitted on the same sixteen clips that suggested it.

What did survive is humbler: stop classifying, start **clustering**. Describe the event region
acoustically and group the variants. It won't tell you which one is good, but it turns twenty seeds
into three representatives without losing the winner — validated on held-out data with known
ground truth. A 5× cut on the listening, not a magic judge.

## What it looks like now

```bash
make emovoice VOICE=ryan     # once: six emotional voice assets, 4 KB each
make emo-06b-demo            # 16 clips: 6 emotions + 5 tags + combinations + a clone
```

Every emotion validated by ear through the shipped flag, under int8. The 1.7B is used exactly once,
offline, to build the assets — and could be replaced by any emotional recording of that voice.

The lesson I'll keep isn't about TTS. We spent months trying to give the small model a capability
it structurally doesn't have — a disentangled emotion subspace — and the answer was to route the
requirement through a capability it *already had in abundance*. The model didn't need to learn
anything. We needed to stop asking the question in the shape the big model had taught us.
